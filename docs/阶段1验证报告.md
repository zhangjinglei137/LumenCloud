## Q1：cloudSaver 容量接口是否存在？（✅ 已闭合 → 数据源选型）

**结论**：cloudSaver **不暴露夸克容量查询接口**。容量数据源改用 **alist `/quark` 目录统计**（用户已拍板）。

**证据**：
1. **源码级**（@librarian 检索 `jiangrui1994/CloudSaver` 开源仓库，9.3k star）：
   - `backend/src/services/QuarkService.ts` 仅实现 4 个方法（getShareInfo/getShareList/getFolderList/saveSharedFile），**无任何容量/配额相关调用**；
   - 全仓检索 `capacity/quota/space/剩余容量` 等关键词**零命中**；路由表无 `/api/quark/space`、`/api/quark/capacity`、`/api/user/space` 等端点；
   - ⚠️ 生产版本（≥0.3，部署于 thntime.fun:8008）源码在私有仓 `MyCloudSaver`，无法直接确认；但开源版契约长期被下游依赖（`Cp0204/quark-auto-save` 等），且黑盒探测佐证。
2. **黑盒探测**（本机直连 thntime.fun:8008，带 token）：7 个常见容量端点（`/api/quark/space`、`/api/quark/capacity`、`/api/quark/disk`、`/api/user/space`、`/api/user/info`、`/api/quark/quota`、`/api/quark/size`）**全部 404**。

**备选数据源对比**（§6.2 优先级失效后）：
| 方案 | 结论 |
|------|------|
| **alist `/quark` 目录统计**（选定） | 只读、零配置、实测成功；/quark 即夸克中转空间，`/api/fs/list` 文件 size 求和 = 真实占用；总容量用 `QUARK_QUOTA_GB` 配置；alist 故障即 fail-closed 不转存 |
| 夸克官方 `capacity/growth/info` API | 真实容量+签到数据，但需夸克 Cookie（cloudSaver 内部持有未暴露，需用户额外提供）；复杂度高、风控风险，放弃 |
| 静态估算 | 仅作前端展示（`source=estimated`），**绝不作转存决策依据**（fail-closed） |

**回写建议**（经确认后）：§6.2 容量数据源改为「alist /quark 目录统计（首选）→ 静态估算（仅展示）」；§15 Q1 标记已解决；§10 cloudSaver 表格补「无容量接口」说明。

## Q2：10G 容量下转存 15G（软超额与否，模型 A/B）（🔍 已实测 2 次，需收敛）

**状态**：已完成 2 次受控实测（D14 流程：报备→确认→转存→核实→清理）。**发现生产版 cloudSaver 的文件夹级转存不落盘**，模型 A/B 判定需据既有实证收敛。

### 实测记录

| # | 测试源 | 大小 | 转存对象 | 结果 |
|---|--------|------|---------|------|
| 1 | `b6357b8c132e` 亮剑(2005)（30 集文件夹） | 15.9G | 文件夹 fid | ❌ task_id 受理，150s 无落盘 |
| 2 | `a158b5be345f` 流浪地球2 4K（文件夹） | 19.5G | 文件夹 fid | ❌ task_id 受理，150s 无落盘 |
| 3a | `a158b5be345f` 同上，递归取单文件 | 164KB (srt) | **具体文件 fid**（n8n 同构） | ✅ **15s 落盘成功**，清理归零 |
| 3b | `a158b5be345f` 同上，递归取单文件 | ~20.8G (mkv 2160p) | 具体文件 fid（n8n 同构） | ❌ 140s 未落盘，/quark 无残留 |

转存目标目录均为 `b1b6bedabb...`（alist Quark root_folder_id 一致，此前 n8n 转存文件可经 alist 可见 → 路径可信）。

### 实证结论

1. **转存机制成立**：单文件级转存（srt 164KB）15s 落盘成功 → fids 必须用**分享内具体文件的 fileId/fileIdToken**（与 n8n «quarkRecursiveGetFiles» 逐文件转存语义一致）；**文件夹 fid 不被生产版落盘**（前 2 轮已证）。
2. **大文件被拒**：同上分享、同构调用，164KB 落盘 vs 20.8G 未落盘 → 高度符合**夸克侧容量门槛**（拒绝超出可用空间的单文件），与你既有实证（9.5G 可再存 3G 达 12.5G、12.5G 后再不能存）一致 → **软超额上限 ≈ 12.5G**，20.8G 必然被拒。无法完全排除「大文件内转更慢」极小概率，但结合 12.5G 上限，容量拒绝为最合理推断。
3. cloudSaver 搜索命中资源几乎全为文件夹结构（亮剑合集、流浪地球2 4K、西游伏妖篇 27G、星游记 178G 等）；递归内层文件 size 字段缺失 → **阶段 3 须递归遍历 + 逐文件转存，文件大小需在递归时从分享总大小/官方面板获取或转存前确认**。
4. 本次第 1/2 次实测未产生容量数据；第 3 次产生关键对照（小文件成/大文件拒）。

### 模型判定（✅ 已定：模型 B——硬上限）

**用户手动实测确认**：夸克为**硬上限**（「确实存不进去」→ 扩容至 210G）。与自动实测证据链一致（164KB 落盘 vs 20.8G 被拒，同构调用排除方式问题）。

- **模型 B（预算）**：`used + file_size + 安全余量 ≤ quota` 才放行，否则 pending + quota_reject_count++。
- 配额：`quark_quota_gb` **默认值 10**（config 默认 / .env.example），**当前部署按扩容后实际空间在本地 `.env` 设 `QUARK_QUOTA_GB=210`**。
- 安全余量建议：`quota × 5%`（210G → ~10G），可经 system_config `capacity_safety_margin_gb` 调。
- semantics：阶段 3 实现 `capacity_provider.check()` 时按模型 B 落地，保留可切换结构（设计文档 §6.3 已回写）。

## Q3：`/api/quark/save` 的 receiveCode 语义（✅ 已闭合）

**结论**：`POST /api/quark/save` 的 **`receiveCode` = `stoken`**（n8n 现状传 stoken **正确**，P7 无需修改）。

**证据**（@librarian 源码级，`jiangrui1994/CloudSaver`）：
- `backend/src/types/cloud.ts`：`SaveFileParams.receiveCode?` 注释为「分享文件的密码」；
- `backend/src/services/QuarkService.ts` `saveSharedFile`：`stoken: params.receiveCode` 直传夸克官方 `/1/clouddrive/share/sharepage/save`；
- 完整链路：`GET /api/quark/share-info?shareCode=...&receiveCode=<提取码>` → 后端用提取码（passcode）换 `stoken` → 前端把 **stoken 作为 receiveCode** 回填 `/api/quark/save`。

**⚠️ 重要区分（两端点同名不同义）**：
| 端点 | receiveCode 语义 |
|------|-----------------|
| `GET /api/quark/share-info` | 分享**提取码 passcode**（可选，无密码分享可省略） |
| `POST /api/quark/save` | **stoken**（来自 share-info 响应，勿传提取码） |

**服务层落实**：`cloudsaver.share_info(share_code, receive_code=提取码)` 与 `cloudsaver.save(params)`（receiveCode=stoken）已按此实现。
**附带发现**：cloudSaver token 有效期 **6h**（JWT，`expiresIn: "6h"`），服务层已实现失效自动重登（仅内存缓存）。

**回写建议**（经确认后）：§15 Q3 标记已解决；§10 cloudSaver 表格补 receiveCode 语义说明；§9.1 脱敏清单中 `receive_code` 实际为 stoken，保留隐藏策略不变。

## 附：验证过程中的其他事实（供回写参考）

1. **搜索源特性**：cloudSaver `/api/search` 为多频道聚合（Telegram 等），**结果不稳定**（同一关键词串行多次：0/0/24 频道）、固定耗时 ~40s。设计文档 §4.3 `searched` 语义（区分「确无资源」vs「没搜到」）已正确处理：本轮没搜到 → task_run(skipped) → 下轮自动重试。
2. **分享源结构**：多为**文件夹结构**（如「亮剑(2005)4K」单文件夹 60G），当前 scan 仅列根目录不递归——三重匹配无法命中文件夹内具体集。对应 P9「全量/剧集模式」权衡，建议阶段 3 补递归遍历（对齐 n8n `quarkRecursiveGetFiles`）。
3. **真实链路验证（阶段 2 骨架）**：Emby 基线 → 搜索 → 分享码 → share-info → share-list → 入队落库 → 幂等 全链路通过；fail-safe（失效源跳过/Emby 故障暂停/recover_on_boot 回退）行为正确。
