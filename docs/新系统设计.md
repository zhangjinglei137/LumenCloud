# LumenCloud 新系统设计文档

> **拾光云映 LumenCloud** —— 自建影视下载管理系统，替代 n8n 流程体系。
> 本文档是系统的完整设计蓝图，基于与用户逐条确认的共识 + 架构审查（Oracle）结论。
> 仓库自空壳重建：`zhangjinglei137/LumenCloud`，Docker Compose 发布 Docker Hub。

---

## 一、设计目标与范围

### 1.1 背景

用户原以 n8n 运行 6 个流程自动补全影视库（现状见 [`现状流程梳理.md`](./现状流程梳理.md)），
受限于：每小时空跑、夸克网盘仅 10G 中转空间、推送噪音、难以排查等 21 个已知问题。
决定弃用 n8n，自建 **LumenCloud**：带 Web 界面、可添加影视名称关联 TMDB、自动搜索下载入库的完整系统。

### 1.2 核心能力（用户故事级）

1. **影视管理**：管理员添加影视（TMDB 搜索选定）→ 入库 → 系统自动巡检补集；访客提交「想看」→ 管理员审批 → 入库下载
2. **容量感知下载**：夸克网盘 10G 中转空间下，搜索与转存解耦为队列，按容量门槛分批转存，下载完成即释放空间
3. **大小约束**：剧集单集 ≤ 1.5G、电影 ≤ 5G（默认，可覆盖），超限文件在搜索筛选阶段即排除
4. **全链路监控**：Web 界面可视化影视状态、队列任务、运行日志；PushPlus 可选通知

### 1.3 非目标（明确不做）

- ❌ 不做播放器/流媒体服务（播放交给 Emby）
- ❌ 不做 Electron 桌面端（Web + PWA 足够，已确认砍掉）
- ❌ 不做多 Worker 分布式（单容器单进程，串行转存）
- ❌ 不重建 n8n 的图形化流程编排（逻辑固化在代码中）

### 2.2 关键架构决策（ADR 摘要）

| 决策 | 结论 | 理由 |
|------|------|------|
| 进程模型 | **单进程**：uvicorn `--workers 1` + 内嵌 AsyncIOScheduler（MemoryJobStore） | Oracle 高1：多进程共享数据库存在锁/连接竞争；任务持久化靠业务表而非 jobstore |
| 数据库 | **PostgreSQL 16（compose 内置 `db` 服务）**，双后端支持（`DATABASE_URL` 指向 SQLite 亦可） | 开箱即用；SQLAlchemy 双后端切换；迁移工具一次性导入旧 media |
| 队列 | 不用消息队列，**数据库队列表 + 单 worker 消费** | 去 Redis；低频负载；任务状态可查询可恢复 |
| 调度 | APScheduler AsyncIOScheduler 单进程内嵌 | 替代 n8n scheduleTrigger 与各 Wait 轮询 |
| 外部依赖 | TMDB/Emby/cloudSaver/alist/aria2/NasTools 保留；**去 Redis**；PushPlus 可选 | 已有服务网络；Redis 仅缓存 token，改**仅内存缓存**（重启重新登录，D6 已定） |
| 转存并发 | **串行**（单 worker 逐任务） | 避免 cloudSaver/aria2 并发压力；容量门槛天然串行化 |

## 三、数据模型（SQLite 表设计）

> 注：`DATABASE_URL` 未设置或为 sqlite 时用内置 SQLite；设置 `DATABASE_URL=postgresql+asyncpg://...` 时切换 Postgres。部署默认走 compose 内置 PostgreSQL 16（§11.1），`alembic upgrade head` 随启动自动执行。

### 3.1 核心表

**media —— 影视清单**（承接旧 `media` 表）

```sql
CREATE TABLE media (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    title         TEXT NOT NULL,            -- 影视名称
    tmdb_id       INTEGER,                  -- TMDB id（审批通过/添加时写入）
    media_type    TEXT,                     -- movie / tv（来自 TMDB，决定大小限制类别）
    status        TEXT NOT NULL DEFAULT 'tracking',  -- tracking/downloading/paused/error
    scan_interval_minutes INTEGER DEFAULT 60,        -- 单影视巡检间隔（热播剧可调）
    max_episode_size_gb REAL,                -- 覆盖全局：剧集单集上限（可空→用全局）
    max_movie_size_gb   REAL,                -- 覆盖全局：电影上限（可空→用全局）
    in_emby       BOOLEAN DEFAULT FALSE,     -- 是否已在 Emby（剧集模式/全量模式依据）
    poster_path   TEXT,                      -- TMDB 海报相对路径（影视库展示用）
    last_scan_at  DATETIME,
    created_at    DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at    DATETIME DEFAULT CURRENT_TIMESTAMP
);
-- media.status 生命周期：
--   tracking（正常巡检）──任一集进入转存/下载──▶ downloading（该影视有进行中任务）
--   downloading ──全部任务结束（done/failed）──▶ tracking
--   tracking/downloading ──手动暂停──▶ paused ──手动恢复──▶ tracking
--   scanning 失败超阈值 ──▶ error ──手动重置或下轮自动尝试──▶ tracking
-- 🚫 扫描跳过规则仅针对 paused / error；downloading 状态不得跳过扫描（否则卡死永不恢复），
--    巡检逻辑改为「有进行中任务则本轮跳过入队/转存，但继续检查遗漏集」
```

**episode_state —— 派发状态（状态机）**（替代 config 表 JSON，根治 P2）

```sql
CREATE TABLE episode_state (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    media_id    INTEGER NOT NULL REFERENCES media(id),
    episode     TEXT NOT NULL,        -- S01E01 / 全量模式=文件名
    state       TEXT NOT NULL,        -- queued / transferring / downloading / done / failed
    file_name   TEXT,                 -- 对应的网盘文件名
    file_size   INTEGER,              -- 字节
    share_code  TEXT,                 -- 来源分享码
    quark_path  TEXT,                 -- 转存到夸克的路径
    aria2_gid   TEXT,                 -- aria2 任务 GID
    retry_count INTEGER DEFAULT 0,
    error       TEXT,                 -- 失败原因（failed 态填写）
    updated_at  DATETIME,
    UNIQUE(media_id, episode)
);
-- 防重规则：queued/transferring/downloading 三态视为已处理，不重复入队；
-- transferring/downloading 超时(如 2h 无进展) → 回退 queued 重试（重试前清理夸克残留）
-- failed 态 = 确定性失败（分享失效/文件不存在等），retry_count ≥ 3 后转入，需人工 retry（API /api/queue/{id}/retry）
```

**ⓘ 双表状态联动约定（防重权威源 = episode_state）**：
- `transfer_queue` 是**执行流视图**（入队/转存/下载的工作记录），`episode_state` 是**防重权威源**
- 状态同步由 `process_transfer_queue` worker 单点驱动：队列每到一个新状态，同步写 episode_state 对应状态
- 「5 态」是同一生命周期在两张表中的各自表达（两表状态名错位一格，`queued ↔ pending`），对应关系如下：

| EpisodeState（防重权威源） | TransferQueue（执行流视图） | 含义 |
|---|---|---|
| `queued` | `pending` | 已入队，等待容量放行后转存（quota 拒绝时保持 pending 且 `quota_reject_count++`，不消耗 retry_count） |
| `transferring` | `transferring` | cloudSaver 转存到夸克中（save 已受理，记录 `save_task_id`） |
| `downloading` | `downloading` | aria2 下载中（记录 `aria2_gid` / `quark_path`） |
| `done` | `done` | 下载完成，待 Emby 二次确认入库（确认前仍参与防重） |
| `failed` | `failed` | 确定性失败（retry ≥ 3 / done 未入库达循环上限），需人工 retry |

- **冲突裁决**：以 episode_state 为准做防重判断；启动恢复（recover_on_boot）时若两表不一致，重建以执行流实际结果为准（查询 aria2 GID/夸克路径核实）

**transfer_queue —— 容量感知转存队列**（搜索与转存解耦）

```sql
CREATE TABLE transfer_queue (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    media_id    INTEGER NOT NULL REFERENCES media(id),
    episode     TEXT NOT NULL,
    file_name   TEXT NOT NULL,
    file_size   INTEGER NOT NULL,     -- 字节（share-info 获取）
    share_code  TEXT NOT NULL,
    pwd_id      TEXT, stoken TEXT, receive_code TEXT,   -- 转存所需凭据
    fids        TEXT, fid_tokens TEXT, folder_id TEXT,  -- JSON 数组字符串
    save_task_id TEXT,              -- cloudSaver save 受理返回的任务 id（save 幂等标记，P2-10）
    status      TEXT NOT NULL DEFAULT 'pending',  -- pending/transferring/downloading/done/failed
    quota_reject_count INTEGER DEFAULT 0,          -- 因容量不足被拒次数
    error       TEXT,
    enqueued_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at  DATETIME,
    UNIQUE(media_id, episode)                      -- 幂等键：同影视同集只允许一条队列记录（未完成前）
);
CREATE INDEX idx_tq_status ON transfer_queue(status);
CREATE INDEX idx_tq_media ON transfer_queue(media_id);
```
**入队幂等约定**：入队走**事务内「检查并写入」**——先查 `episode_state` 是否已有 queued/transferring/downloading/failed(done 未确认) 记录，存在则跳过；所有状态转移用条件更新（`UPDATE ... WHERE state='queued'` 捕获行级冲突）；手动扫描、定时扫描、recover 恢复共享同一 media 级扫描锁，杜绝并发双入队/重复转存。

## 四、调度与队列设计

### 4.1 进程模型（Oracle 修正：单进程）

- `CMD` 或 supervisord 仅启动 **一个 uvicorn 进程**（`--workers 1`）
- 应用启动时（lifespan）初始化 `AsyncIOScheduler(jobstore=MemoryJobStore)`
- **任务状态不依赖 APScheduler jobstore**：每次任务执行写 `task_run` 表；**lifespan startup 阶段执行 `recover_on_boot()`**——扫描 episode_state/transfer_queue，将超时未完成的 transferring/downloading 回退 queued（超时阈值 `episode_state_timeout_hours`，默认 2h）
- **执行模型**：`process_transfer_queue` 由**单一 asyncio task 串行消费**（转存必须串行化，避免容量竞争与 cloudSaver 压力）；其余 job（scan_all_media / nastools_sync / release_space_cleanup / notification_scan）可并发执行
- 不用独立 ARQ worker（已去 Redis）

### 4.2 调度任务清单

| 任务 | 调度 | 说明 |
|------|------|------|
| `scan_all_media` | **每分钟 tick**（内部到期检查） | 调度入口固定每分钟触发；是否巡检某影视由内部判断（`last_scan_at + scan_interval_minutes ≤ now`），支持单影视可调间隔 |
| `process_transfer_queue` | 事件触发 + 每分钟兜底 | 队列非空且容量允许时取一个 pending 转存 |
| `nastools_sync` | 下载完成事件触发 | 带冷却（`nastools_sync_cooldown_minutes=30`）；冷启动检测 |
| `release_space_cleanup` | 每 12 小时兜底 | 检查夸克残留孤儿文件（正常流程靠「下载完成即释放」） |
| `notification_scan` | 每 5 分钟 | 检查待审批 watch_requests / 失败任务 → Notifier 推送 |

### 4.3 影视巡检主流程（替代「定时所有影视 + 影视下载」）

```
scan_all_media(media)
 ├─ 1. 状态预检：media.status != tracking → 跳过
 ├─ 2. Emby 查已有集：shows/missing → missing_codes（防重基线）
 │        ├─ 无遗漏 → 记录 task_run(skipped) → 结束（消灭 P3 空跑）
 │        ├─ 有遗漏 → 进入搜索阶段
 │        ├─ Emby 未收录该剧（基线不可用）→ **默认跳过防盲入**；**可配置为不跳过**：
 │        │    不硬性阻断——跳过防重检查、任务照常执行（Emby 收录后由后续巡检正常接管，
 │        │    凭 episode_state 防重态防重复入队）
 │        └─ Emby 故障（超时/5xx）→ **fail-safe，不进入新缺集发现**：
 │            仅允许继续处理 episode_state 中已存在且处于 queued/failed-retry 的既有任务；
 │            新的缺集发现暂停并记录 task_run(error)，等 Emby 恢复建立基线后再继续
 │            （原因：Emby 同时承担已有集基线+防重依据，故障时继续搜索会重复转存/误占空间）
 ├─ 3. cloudSaver 搜索 → 提取分享码（加分匹配 + 限数 20）→ share-info
 ├─ 4. 大小过滤：episode>max_episode_size_gb 或 movie>max_movie_size_gb → 跳过并记录
 ├─ 5. 匹配缺失集（三重匹配：SxxExx / SxxExxx / 第N集）
 ├─ 6. 候选写入 transfer_queue(pending)，写入 episode_state(queued) → 触发 process_transfer_queue
 └─ 7. 记录 task_run
```

### 4.4 容量感知转存（核心新逻辑）

```
process_transfer_queue()
 ├─ 1. 取最早 pending 的 transfer_queue 任务（串行，单 worker）
 ├─ 2. 读取夸克当前容量（**alist `/quark` 目录统计**——Q1 结论：cloudSaver 无容量接口，
 │      实时数据源 = alist，静态估算仅作展示；容量不可用一律 fail-closed 不转存）
 ├─ 3. 门槛判断（实证待定，见 §6.3）：
 │      模型A（软超额）：used < quota → 允许转存（短暂超额由下载释放兜底）
 │      模型B（预算）：   used + file_size + 安全余量 ≤ quota → 允许
 │      → 不满足 → 任务保持 pending + quota_reject_count++ → 等待空间释放后兜底重试
 ├─ 4. 转存（cloudSaver /api/quark/save）→ episode_state → transferring
 ├─ 5. 经 alist 取直链 → aria2 addUri → 记录 GID → episode_state → downloading
 ├─ 6. aria2 tellStatus 轮询直至 complete（文件落盘 /downloads）
 ├─ 7. 下载完成：更新状态 done → 从夸克删除该文件（确认无其他 downloading 任务引用后）
 ├─ 8. 释放容量 → 触发下一 pending 任务 + 若该影视全部完成则触发 nastools_sync
 └─ 9. 写 task_run
```

### 4.5 状态机防重（Oracle 修正：5 态）

```
                     ┌─────────────────────────────────────────────┐
                     ▼                                             │
queued ──转存──▶ transferring ──提交aria2──▶ downloading ──完成──▶ done
                     │                              │              │
                     └────────超时(2h)──────────────┘              │
                           │ 回退 queued + 清理夸克残留             │
                           ▼                                       │
                      （retry_count++）                            │
                     downloading/transferring ──确定性失败──▶ failed
                     failed ──人工 retry（/api/queue/{id}/retry）──▶ queued
                     done ──Emby 二次确认入库（未确认前仍参与防重）
```

- **retry 计数规则**：仅「确定性失败」与「超时回退」消耗 `retry_count`；**容量门槛拒绝（quota_reject_count）不消耗 retry_count**，二者字段分离；`retry_count ≥ 3` 转入 `failed`，需人工 retry，人工 retry 时重置 `retry_count=0`
- **防重检查**（Emby missing + episode_state）：`queued/transferring/downloading` 均视为已处理，不重复入队；**`done` 后到 Emby 二次确认入库前仍视为已处理**（防「下载完成但 NasTools 未同步/Emby 未刷新」窗口期重复下载），Emby 确认后解除防重，重新参与遗漏检查
- **quota 拒绝**：任务保持 `pending`，`quota_reject_count++`，不进入失败路径（等空间释放后兜底续跑）

## 六、容量与大小限制

### 6.1 大小限制（搜索筛选阶段）

| 类别 | 默认上限 | 判定依据 | 覆盖方式 |
|------|---------|---------|---------|
| 剧集（tv） | 每集 ≤ 1.5G | TMDB media_type=tv | media.max_episode_size_gb |
| 电影（movie）| ≤ 5G | TMDB media_type=movie | media.max_movie_size_gb |

- 过滤时机：`提取缺失集` 匹配到候选文件时，`file_size > 上限` → 跳过该文件（不入队），记日志
- 全局默认存 `system_config`，单影视覆盖存 media 表（可空回落全局）

### 6.2 容量阈值（转存阶段）

- 配额默认 `quark_quota_gb=10`（system_config 可调，Phase 8 起可在**设置页直接配置**，保存即生效）；**当前部署：用户已扩容至 210G，设为 `quark_quota_gb=210`（默认值仍为 10，按实际空间覆盖）**
- **实时容量读取**（§4.4 步骤 2）：**alist `/quark` 目录统计**（阶段 1 实证结论：cloudSaver 无容量接口）；静态估算仅作展示（`/api/capacity` 的 `source=estimated`）。`quark_capacity_log` 仅作**快照记录**（每次检查后的归档），不作为实时数据源
- **fail-closed 容量策略**：实时容量不可用/单位不明/文件大小未知时，**一律默认不转存（保持 pending）**，绝不用估算值放行——容量数据源估错即超额，宁可等容量接口恢复
- 单容器单 worker 串行转存 → 无并发容量竞争；后续若加并发必须用进程内锁串行化「容量检查→转存」两步

### 6.3 容量门槛模型（**实证已定：模型 B——硬上限**）

> **阶段 1 实证结论（2026-09-05）**：夸克为**硬上限**。
> 证据链：①被测环境 10G 时转存 ~20.8G 单文件被拒（task_id 受理但 140s 不落盘）；②用户手动测试确认「存不进去」；③srt 164KB 同构调用 15s 落盘成功（排除调用方式问题）→ 容量拒绝是唯一合理解释。
> 用户决定：**夸克空间已扩容至 210G**；`quark_quota_gb` 默认值保持 10，**当前部署设为 210**（Phase 8 起在设置页配置 `quark_quota_gb`，保存即生效；早期部署曾用 `.env` 的 `QUARK_QUOTA_GB` 覆盖，现仅作 fallback）。

- **模型 B（预算）**：`used + file_size + 安全余量 ≤ quota` 才允许转存，否则 `pending + quota_reject_count++`，等待空间释放后兜底重试
- 实现上把判断封装为 `capacity_provider.check(candidate_bytes) -> bool`，模型已定 B，仍保留可切换结构避免后续返工
- 安全余量建议：`quota × 5%`（210G → ~10G 富余），可经 system_config `capacity_safety_margin_gb` 调

## 九、API 清单（REST）

### 9.1 API 敏感字段脱敏与权限契约

- **响应 DTO 强制**：`/api/queue`、`/api/media/{id}` 等含 `transfer_queue` 数据的接口**不得直接返回表记录**；`stoken`、`receive_code`、`fid_tokens`、`pwd_id`、`share_code`、`folder_id` 为网盘凭据，guest 一律隐藏，admin 仅在前端确需展示时脱敏回显（如 `share_code` 后 4 位）
- **配置接口（Phase 8）**：`/api/settings` 仅 admin；`GET` 返回 `system_config` 全量（**敏感键以 `***` 占位回显**，绝不回显明文，见 `config_store._SENSITIVE_KEYS`）+ `services` 凭据「是否已配置」布尔 + `editable_keys` 可配置键清单；`PATCH` 白名单 UPSERT，**服务凭据保存即生效**（commit 后刷新进程内配置缓存，无需重启），非白名单键 422
- **写操作鉴权**：`retry`、`approve/reject`、`invites`、`settings`、`media` 增删改 全部服务端校验 `role=admin`；访客仅可读列表 + 提交 `watch_requests`
- **邀请码消耗原子性**：注册时（校验码 + 标记 used + 建用户）在同一事务内完成，并用条件更新 `UPDATE invite_codes SET used_by=?, used_at=? WHERE code=? AND used_by IS NULL` 防并发复用
- **日志脱敏**：`/api/logs` 与 task_run 中不得记录 token/凭据明文

## 十二、迁移与并行切换

### 12.1 数据迁移（一次性脚本 `scripts/migrate_from_n8n.py`）

- 输入：n8n 的 Postgres `media` 表（11 部影视）
- **字段映射**：旧表 `media.title` → 新表 `media.title`；旧表 `media.tmdb_id` → 新表 `media.tmdb_id`；`media_type` 从 TMDB 补查（查询失败则该条标记为待补，不中断整体迁移）；大小上限用全局默认
- **幂等性**：迁移脚本可重复执行；以 `tmdb_id`（或 title 归一化）为幂等键，已存在则跳过
- **回滚**：迁移前自动导出备份（`media_export_<timestamp>.json`）；新系统提供 `DELETE FROM media` 重置命令配合回滚
- **不迁移**：`episode_state`（防重靠 Emby 重新建立基线，首轮巡检会重建）、config 凭据（Phase 8 起在设置页配置入库，env 仅作 fallback）、cloud_189_users
- 迁移脚本在容器内执行：`docker exec lumencloud python scripts/migrate_from_n8n.py --dsn postgresql://...`（**脚本随阶段 2 打包进镜像**：Dockerfile 增加 `COPY scripts /app/scripts`）
- ⚠️ 依赖说明：默认 SQLite 镜像必须同时安装 `asyncpg`（连接旧 Postgres 读取 media 表）；已列入 `backend/requirements.txt`
- **SQLite/Postgres 双后端 DDL 方案**：文档 SQL 仅为 SQLite 语法参考；实际建表走 SQLAlchemy 模型（主键用 `BigInteger + Identity` 兼容双后端），不直接执行文档 DDL；两个后端分别跑一次迁移测试
