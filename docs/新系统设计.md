# LumenCloud 新系统设计文档

> **拾光云映 LumenCloud** —— 自建影视下载管理系统，替代 n8n 流程体系。
> 本文档是系统的完整设计蓝图，基于与用户逐条确认的共识 + 架构审查（Oracle）结论。
> 仓库自空壳重建：`zhangjinglei137/LumenCloud`，单容器发布 Docker Hub。

---

## 一、设计目标与范围

### 1.1 背景

用户原以 n8n 运行 6 个流程自动补全影视库（现状见 [`现状流程梳理.md`](./现状流程梳理.md)），
受限于：每小时空跑、夸克网盘仅 10G 中转空间、推送噪音、难以排查等 21 个已知问题。
决定弃用 n8n，自建 **LumenCloud**：带 Web 界面、可添加影视名称关联 TMDB、自动搜索下载入库的完整系统。

### 1.2 核心能力（用户故事级）

1. **影视管理**：管理员添加影视（TMDB 搜索选定）→ 入库 → 系统自动巡检补集；访客提交「想看」→ 管理员审批 → 入库下载
2. **容量感知下载**：夸克网盘 10G 中转空间下，搜索与转存解耦为队列，按容量门槛分批转存，下载完成即释放空间
3. **大小约束**：剧集单集 ≤ 1.5G、电影 ≤ 5G（默认，可覆盖），超限文件在搜索筛选阶段即排除
4. **全链路监控**：Web 界面可视化影视状态、队列任务、运行日志；PushPlus 可选通知

### 1.3 非目标（明确不做）

- ❌ 不做播放器/流媒体服务（播放交给 Emby）
- ❌ 不做 Electron 桌面端（Web + PWA 足够，已确认砍掉）
- ❌ 不做多 Worker 分布式（单容器单进程，串行转存）
- ❌ 不重建 n8n 的图形化流程编排（逻辑固化在代码中）

### 2.2 关键架构决策（ADR 摘要）

| 决策 | 结论 | 理由 |
|------|------|------|
| 进程模型 | **单进程**：uvicorn `--workers 1` + 内嵌 AsyncIOScheduler（MemoryJobStore） | Oracle 高1：多进程共享 SQLite 会锁冲突；任务持久化靠业务表而非 jobstore |
| 数据库 | **SQLite 默认**（WAL，volume 持久化），可选外部 Postgres | 单容器开箱即用；SQLAlchemy 双后端切换；迁移工具一次性导入旧 media |
| 队列 | 不用消息队列，**数据库队列表 + 单 worker 消费** | 去 Redis；低频负载；任务状态可查询可恢复 |
| 调度 | APScheduler AsyncIOScheduler 单进程内嵌 | 替代 n8n scheduleTrigger + ARQ cron |
| 外部依赖 | TMDB/Emby/cloudSaver/alist/aria2/NasTools 保留；**去 Redis**；PushPlus 可选 | 已有服务网络；Redis 仅缓存 token，改内存+DB |
| 转存并发 | **串行**（单 worker 逐任务） | 避免 cloudSaver/aria2 并发压力；容量门槛天然串行化 |

## 三、数据模型（SQLite 表设计）

> 注：`DATABASE_URL` 未设置或为 sqlite 时用内置 SQLite；设置 `DATABASE_URL=postgresql+asyncpg://...` 时切换 Postgres。

### 3.1 核心表

**media —— 影视清单**（承接旧 `media` 表）

```sql
CREATE TABLE media (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    title         TEXT NOT NULL,            -- 影视名称
    tmdb_id       INTEGER,                  -- TMDB id（审批通过/添加时写入）
    media_type    TEXT,                     -- movie / tv（来自 TMDB，决定大小限制类别）
    status        TEXT NOT NULL DEFAULT 'tracking',  -- tracking/downloading/paused/error
    scan_interval_minutes INTEGER DEFAULT 60,        -- 单影视巡检间隔（热播剧可调）
    max_episode_size_gb REAL,                -- 覆盖全局：剧集单集上限（可空→用全局）
    max_movie_size_gb   REAL,                -- 覆盖全局：电影上限（可空→用全局）
    in_emby       BOOLEAN DEFAULT FALSE,     -- 是否已在 Emby（剧集模式/全量模式依据）
    last_scan_at  DATETIME,
    created_at    DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at    DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

**episode_state —— 派发状态（4 态状态机）**（替代 config 表 JSON，根治 P2）

```sql
CREATE TABLE episode_state (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    media_id    INTEGER NOT NULL REFERENCES media(id),
    episode     TEXT NOT NULL,        -- S01E01 / 全量模式=文件名
    state       TEXT NOT NULL,        -- queued / transferring / downloading / done
    file_name   TEXT,                 -- 对应的网盘文件名
    file_size   INTEGER,              -- 字节
    share_code  TEXT,                 -- 来源分享码
    quark_path  TEXT,                 -- 转存到夸克的路径
    aria2_gid   TEXT,                 -- aria2 任务 GID
    retry_count INTEGER DEFAULT 0,
    updated_at  DATETIME,
    UNIQUE(media_id, episode)
);
-- 防重规则：queued/transferring/downloading 三态视为已处理，不重复入队；
-- transferring/downloading 超时(如 2h 无进展) → 回退 queued 重试（重试前清理夸克残留）
```

**transfer_queue —— 容量感知转存队列**（搜索与转存解耦）

```sql
CREATE TABLE transfer_queue (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    media_id    INTEGER NOT NULL REFERENCES media(id),
    episode     TEXT NOT NULL,
    file_name   TEXT NOT NULL,
    file_size   INTEGER NOT NULL,     -- 字节（share-info 获取）
    share_code  TEXT NOT NULL,
    pwd_id      TEXT, stoken TEXT, receive_code TEXT,   -- 转存所需凭据
    fids        TEXT, fid_tokens TEXT, folder_id TEXT,  -- JSON 数组字符串
    status      TEXT NOT NULL DEFAULT 'pending',  -- pending/transferring/downloading/done/failed
    quota_reject_count INTEGER DEFAULT 0,          -- 因容量不足被拒次数
    error       TEXT,
    enqueued_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at  DATETIME
);
CREATE INDEX idx_tq_status ON transfer_queue(status);
CREATE INDEX idx_tq_media ON transfer_queue(media_id);
```

**download_task —— 下载任务**（aria2 任务跟踪）

```sql
CREATE TABLE download_task (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    media_id      INTEGER REFERENCES media(id),
    transfer_id   INTEGER REFERENCES transfer_queue(id),
    episode       TEXT,
    file_name     TEXT,
    aria2_gid     TEXT,
    status        TEXT NOT NULL DEFAULT 'downloading',  -- downloading/complete/failed
    local_path    TEXT,               -- /downloads/...
    quark_path    TEXT,               -- /quark/...（删除用）
    downloaded_at DATETIME,
    created_at    DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

**task_run —— 任务执行记录**（替代 n8n 执行历史）

```sql
CREATE TABLE task_run (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    task_type   TEXT NOT NULL,        -- scan_media / transfer / sync_nastools / cleanup / notify
    media_id    INTEGER,
    status      TEXT,                 -- success / skipped / error
    message     TEXT,
    started_at  DATETIME,
    finished_at DATETIME
);
```

**quark_capacity_log —— 容量快照**（门槛判断数据源）

```sql
CREATE TABLE quark_capacity_log (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    total_gb   REAL,                  -- 总容量（默认 10）
    used_gb    REAL,                  -- 已用
    source     TEXT,                  -- cloudsaver / alist / estimated
    checked_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

## 四、调度与队列设计

### 4.1 进程模型（Oracle 修正：单进程）

- `CMD` 或 supervisord 仅启动 **一个 uvicorn 进程**（`--workers 1`）
- 应用启动时（lifespan）初始化 `AsyncIOScheduler(jobstore=MemoryJobStore)`
- **任务状态不依赖 APScheduler jobstore**：每次任务执行写 `task_run` 表；重启后按表内状态恢复（如将超时未完成的 episode_state 回退 queued）
- 不用独立 ARQ worker（已去 Redis）

### 4.2 调度任务清单

| 任务 | 调度 | 说明 |
|------|------|------|
| `scan_all_media` | 每分钟触发（内部检查是否到期）或每小时 | 遍历 media，按 `scan_interval_minutes` 决定是否本轮巡检该影视 |
| `process_transfer_queue` | 事件触发 + 每分钟兜底 | 队列非空且容量允许时取一个 pending 转存 |
| `nastools_sync` | 下载完成事件触发 | 带冷却（`nastools_sync_cooldown_minutes=30`）；冷启动检测 |
| `release_space_cleanup` | 每 12 小时兜底 | 检查夸克残留孤儿文件（正常流程靠「下载完成即释放」） |
| `notification_scan` | 每 5 分钟 | 检查待审批 watch_requests / 失败任务 → Notifier 推送 |

### 4.3 影视巡检主流程（替代「定时所有影视 + 影视下载」）

```
scan_all_media(media)
 ├─ 1. 状态预检：media.status != tracking → 跳过
 ├─ 2. Emby 查已有集：shows/missing → missing_codes（防重基线）
 │        ├─ 无遗漏 → 记录 task_run(skipped) → 结束（消灭 P3 空跑）
 │        └─ 有遗漏 → 进入搜索阶段
 ├─ 3. cloudSaver 搜索 → 提取分享码（加分匹配 + 限数 20）→ share-info
 ├─ 4. 大小过滤：episode>max_episode_size_gb 或 movie>max_movie_size_gb → 跳过并记录
 ├─ 5. 匹配缺失集（三重匹配：SxxExx / SxxExxx / 第N集）
 ├─ 6. 候选写入 transfer_queue(pending)，写入 episode_state(queued) → 触发 process_transfer_queue
 └─ 7. 记录 task_run
```

### 4.4 容量感知转存（核心新逻辑）

```
process_transfer_queue()
 ├─ 1. 取最早 pending 的 transfer_queue 任务（串行，单 worker）
 ├─ 2. 读取夸克当前容量（cloudsaver 容量接口，探索任务；备选 alist / 静态估算）
 ├─ 3. 门槛判断（实证待定，见 §6.3）：
 │      模型A（软超额）：used < quota → 允许转存（短暂超额由下载释放兜底）
 │      模型B（预算）：   used + file_size + 安全余量 ≤ quota → 允许
 │      → 不满足 → 任务保持 pending + quota_reject_count++ → 等待空间释放后兜底重试
 ├─ 4. 转存（cloudSaver /api/quark/save）→ episode_state → transferring
 ├─ 5. 经 alist 取直链 → aria2 addUri → 记录 GID → episode_state → downloading
 ├─ 6. aria2 tellStatus 轮询直至 complete（文件落盘 /downloads）
 ├─ 7. 下载完成：更新状态 done → 从夸克删除该文件（确认无其他 downloading 任务引用后）
 ├─ 8. 释放容量 → 触发下一 pending 任务 + 若该影视全部完成则触发 nastools_sync
 └─ 9. 写 task_run
```

### 4.5 状态机防重（Oracle 修正：4 态）

```
                  ┌────────────────────────────────────────────┐
                  ▼                                            │
queued ──转存──▶ transferring ──提交aria2──▶ downloading ──完成──▶ done
                  │                              │
                  └─────────超时(2h)─────────────┘
                        │ 回退 queued + 清理夸克残留
                        ▼
                   （重试，retry_count++）
```

- 防重检查（Emby missing + episode_state）：`queued/transferring/downloading` 均视为已处理，不重复入队
- `done` 后由 Emby 二次确认入库；7 天过期仅对 done 后的「重新检查遗漏」生效

## 五、鉴权与审批流

### 5.1 角色模型

| 角色 | 权限 |
|------|------|
| **admin** | 全部：添加/删除影视、直接触发下载、审批、设置、邀请码生成、查看全部日志 |
| **guest** | 只读浏览 + 提交「想看」请求 + 查看自己请求状态 |

### 5.2 注册与登录

- **邀请码注册**：管理员在设置页生成 `invite_codes` → 访客凭码注册（username + password + invite_code）
- **管理员初始化**：首次启动时（无 admin 用户）提供 `INIT_ADMIN_USERNAME/INIT_ADMIN_PASSWORD` 环境变量创建，或在 SetupWizard 页面完成
- **会话**：JWT（`JWT_SECRET` 来自环境变量），前端 Pinia 存储
- 访客提交「想看」：输入名称 → 实时 TMDB 搜索 → 选定条目 → `watch_requests(pending)`

### 5.3 审批

- 管理员在审批页查看 pending 请求（名称/海报/候选 TMDB）→ **批准**（写入 media 表，status=tracking）或 **拒绝**（填原因）
- 批准/提交时系统向 `notifier` 触发「审批待处理」通知

## 六、容量与大小限制

### 6.1 大小限制（搜索筛选阶段）

| 类别 | 默认上限 | 判定依据 | 覆盖方式 |
|------|---------|---------|---------|
| 剧集（tv） | 每集 ≤ 1.5G | TMDB media_type=tv | media.max_episode_size_gb |
| 电影（movie）| ≤ 5G | TMDB media_type=movie | media.max_movie_size_gb |

- 过滤时机：`提取缺失集` 匹配到候选文件时，`file_size > 上限` → 跳过该文件（不入队），记日志
- 全局默认存 `system_config`，单影视覆盖存 media 表（可空回落全局）

### 6.2 容量阈值（转存阶段）

- 配额默认 `quark_quota_gb=10`（system_config 可调）
- 每次转存前读最新容量（`quark_capacity_log`），容量是动态的
- 单容器单 worker 串行转存 → 无并发容量竞争；后续若加并发必须用进程内锁串行化「容量检查→转存」两步

### 6.3 容量门槛模型（**实证待定决策点**）

> 用户实测：9.5G 占用时可暂存 3G（达 12.5G），12.5G 时不能再存 → 疑似软超额。
> Oracle 认为夸克为硬上限。**阶段 1 必须做真实测试**：10G 容量下尝试转存 15G 电影。

- **测试通过（软超额）** → 模型 A：`used < quota` 即允许转存
- **测试失败（硬上限）** → 模型 B：`used + file_size + 安全余量 ≤ quota` 才转存，否则 pending
- 实现上把判断封装为 `capacity_provider.check(candidate_bytes) -> bool`，两种模型可切换，避免返工

## 七、通知设计（Notifier 抽象）

```python
class Notifier(Protocol):
    async def notify(self, event: NotifyEvent): ...

class PushPlusNotifier:  # 可选，配置 PUSHPLUS_TOKEN 环境变量
    ...

class InAppNotifier:     # 站内消息（前端铃铛），始终启用
    ...

notifier = NotifierChain([InAppNotifier(), PushPlusNotifier()])
```

通知事件（全局开关在 system_config）：

| 事件 | 触发 | 默认 |
|------|------|------|
| `download_complete` | 某影视/某集下载完成 | 开 |
| `flow_error` | 任一流程异常（替代 P6 静默失败） | 开 |
| `approval_pending` | 有新的 watch_requests 待审批 | 开 |
| 空跑/无遗漏 | 不推送（消灭 P1 噪音） | 关 |

**S1 修复**：推送走 HTTP POST（form body 传 token/title/content/template），不再 GET+query 传长 content。

## 十二、迁移与并行切换

### 12.1 数据迁移（一次性脚本 `scripts/migrate_from_n8n.py`）

- 输入：n8n 的 Postgres `media` 表（11 部影视：title、tmdb_id）
- 输出：写入新系统 `media` 表（media_type 需从 TMDB 补查，大小上限用全局默认）
- **不迁移**：`episode_state`（防重靠 Emby 重新建立基线，首轮巡检会重建）、config 凭据（改环境变量）、cloud_189_users
- 迁移脚本在容器内执行：`docker exec lumencloud python scripts/migrate_from_n8n.py --dsn postgresql://...`

### 12.2 并行切换策略

```
阶段① 新系统上线：仅启用【手动触发】巡检，关闭定时
阶段② 手动验证：添加影视 → 手动触发 → 检查转存/下载/入库/通知全链路
阶段③ 稳定后：启用新系统定时巡检；n8n 暂停「定时所有影视」定时触发
阶段④ 观察 1-2 周无重复下载 → 停用 n8n
⚠️ 铁律：并行期绝不允许 n8n 定时 与 新系统定时 同时开启（会重复转存/占用容量）
```
