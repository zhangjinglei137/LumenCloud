> 审查基准：成熟自用产品化（长期运行 / 可能给别人用 / 数据不能丢 / 出问题能快速定位）

> 本文件覆盖主题：A 转存链路与配置开关、B 并发竞态与一致性、C 数据与容量正确性

## A. 转存链路与配置开关

### A-1｜P1｜转存队列缺「完成后续跑」闭环 → 队列静默积压

- **定位**：
  - `backend/app/tasks/transfer.py:893-933` —— `_process_one_pending` 成功路径（步骤 6）无续跑
  - `backend/app/tasks/transfer.py:890` —— 仅**失败非终态回退**才 `_spawn(process_transfer_queue)`
  - `backend/app/tasks/transfer.py:352-355` —— `_complete_download` 只触发 `nastools_sync`，不触发 transfer
  - `backend/app/tasks/scan.py:923-924` —— 一次 scan 只在循环外 `if enqueued:` 触发一次
- **证据**：
  ```python
  # transfer.py:886-891  只有失败回退才续跑
          else:
              # 非终态回退（pending/queued）后触发下一轮消费续跑
              _spawn(process_transfer_queue)
          return
  # 步骤 6（成功，893-933 行）末尾只有 record_task_run(success)，没有续跑调用

  # transfer.py:351-355  下载完成释放后只触发 nastools_sync
      _spawn(nastools_sync.nastools_sync)

  # scan.py:921-924  一次 scan 只触发一次
      if enqueued:
          await _trigger_transfer()
  ```
- **触发路径**：
  1. 一次 scan 为同一部剧入队 N 集（`for cand in candidates` 逐文件 `_enqueue`，`enqueued` 累加），但 `_trigger_transfer()` 只在循环后触发**一次**；
  2. `process_transfer_queue` 串行消费 **1 个** pending（成功转存+提交 aria2）后返回，**不续跑**；
  3. 剩余 N-1 个 pending 的 episode_state 已处于 `queued`（`_ACTIVE_STATES` 内），下次 scan 走 `"existing"` 分支（`scan.py:540-550`），`enqueued=0` → **不触发 transfer**；
  4. 兜底来源 `process_transfer_queue_job` 每分钟触发，但默认 `paused=True`（`scheduler.py:128-135`，叠加 A-2）；
  5. 同理，「容量不足保持 pending 等待释放」的任务（`transfer.py:654-689`），下载完成释放空间后 `_complete_download` 也不触发 transfer 续跑 → **容量恢复后任务不自动重试**。
- **后果**：pending 队列**静默积压**，界面只见队列卡在 pending/queued，无告警。违背设计文档 `docs/新系统设计.md` §4.4 步骤 8「释放容量 → 触发下一 pending 任务」与 §4.2「事件触发 + 每分钟兜底」的明示约定。
- **建议**：步骤 6 成功事务提交后 `_spawn(process_transfer_queue)`（与失败回退对称）；或 `_complete_download` 释放成功后触发一次 `process_transfer_queue`。已有全局 `_process_lock` 串行锁保护，不会引入并发。

## B. 并发、竞态与一致性约定

### B-1｜P1｜`media.status='paused'` 在任务进行中被设置 → 永久死锁在 downloading

- **定位**：
  - `backend/app/tasks/transfer.py:491-519` —— `_sync_media_status`：仅 `WHERE Media.status == "downloading"` 才回退 `tracking`
  - `backend/app/routers/media.py:25` —— PATCH 允许 `tracking/paused` 两个值
  - `backend/app/tasks/scan.py:778` —— paused 时 scan 跳过
- **证据**：
  ```python
  # transfer.py:514-518
      result = await s.execute(
          update(Media)
          .where(Media.id == media_id, Media.status == "downloading")
          .values(status="tracking", updated_at=_now())
      )
  ```
- **触发路径**：admin 在转存/下载进行中 PATCH `status=paused` → 下载继续完成 → `_complete_download` 调 `_sync_media_status` → `WHERE status='downloading'` 不匹配（已是 paused）→ media **永久 downloading**；此后 scan 因 paused 跳过，手工置回 tracking 前不会恢复，前端显示异常。
- **建议**（三选一/组合）：①`_sync_media_status` 的 WHERE 扩展为 `Media.status.in_(("downloading", "paused"))`，且 paused 且无进行中 es 时保持 paused 不强制回退；②PATCH 设置 paused 前检查是否有进行中任务，有则拒绝并明确提示；③运维手册补手工修复指引（见 `审查-文档与流程.md` G-1）。

### B-2｜P1｜`DELETE /api/media/{id}` 与 scan 入队竞态 → 孤儿数据

- **定位**：`backend/app/routers/media.py:367-399`
- **证据**：
  ```python
  # media.py:367-393 前置检查
  if (await session.scalar(select(TransferQueue.id).where(...))
      or await session.scalar(select(EpisodeState.id).where(...))
      or await session.scalar(select(DownloadTask.id).where(...))):
      raise HTTPException(status_code=409, ...)
  # media.py:395-399 删除（检查与删除不在同一锁/事务内）
  await session.execute(delete(EpisodeState)...)
  await session.execute(delete(DownloadTask)...)
  await session.execute(delete(TransferQueue)...)
  await session.delete(media)
  await session.commit()
  ```
- **触发路径**：admin 点删除 → 前置检查通过（无进行中任务）→ 此刻 scan 定时 tick 触发 → `_enqueue` 写入新 episode_state + transfer_queue（`_enqueue` 持 per-media `_scan_locks`，但 `delete_media` 不获取该锁）→ delete_media 执行删除 → 新写入的子表记录成为孤儿（FK 指向已删 media.id，且 FK 无 `ON DELETE CASCADE`）；转存捡起孤儿 pending 后 CAS rowcount=0，白白消费资源。
- **建议**：`delete_media` 先获取 `_scan_locks[media_id]`（或引入统一的 media 级锁）保证检查与删除原子性；或在 `_enqueue` 入口校验 media 存在；数据库层给子表 FK 加 `ON DELETE CASCADE` 兜底。

### B-3｜P1｜recovery 阶段② aria2 副作用在 CAS 失败时不回滚 → 任务卡死 2h

- **定位**：`backend/app/tasks/recovery.py:125-182`
- **证据**：
  ```python
  # 阶段②：事务外清理夸克残留 + 尝试移除 aria2 任务（网络 IO 不放事务内）
  for row in rows:
      if row.aria2_gid:
          try:
              await aria2.client.remove(row.aria2_gid)  # ← 副作用已发生
          except Exception as exc:
              logger.warning(...)
  # 阶段③：新事务逐行 CAS 回退状态
  r_es = await session.execute(
      update(EpisodeState).where(
          EpisodeState.id == row.id,
          EpisodeState.state.in_(_PROGRESS_STATES),
          EpisodeState.retry_count == retry_snapshots[row.id],  # CAS
      )...
  )
  if r_es.rowcount == 0:
      continue  # CAS 冲突 → 跳过回退
  ```
- **触发路径**：
  1. recovery 阶段①快照选中 `es(downloading, updated_at 超 2h)`；
  2. 阶段②执行 `aria2.client.remove(gid)`——**aria2 任务已被移除**；
  3. 与此同时（recovery 在 await 期间）transfer 的 `_fail_download` 并发推进了 `retry_count`；
  4. 阶段③ CAS `WHERE retry_count == 快照值` → rowcount=0 → recovery 跳过回退；
  5. es/tq 仍是 downloading，但 aria2 任务已被移除；transfer 阶段 A 的 `tell_status(gid)` 失败（任务不存在），本轮跳过不刷新 updated_at；
  6. 任务卡在 downloading，直到下一轮 recovery（再过 2h）CAS 成功回退。
- **影响**：任务滞留约 2h（一个 recovery 周期），不丢数据但影响时效。
- **建议**：将 `aria2.remove` 移到阶段③ CAS 成功（rowcount==1）**之后**执行（网络 IO 放 CAS 之后），保持「先校验、后副作用」顺序。

### C-5｜P2｜时间源混用（`onupdate=func.current_timestamp()` vs 应用侧 naive UTC）

- **定位**：`backend/app/models/__init__.py:98`、`140`；`backend/app/tasks/transfer.py:99-101`
- **证据**：
  ```python
  # models/__init__.py:98 (EpisodeState.updated_at) / :140 (TransferQueue.updated_at)
      updated_at = mapped_column(DateTime, onupdate=func.current_timestamp())
  # transfer.py:99-101
  def _now() -> datetime:
      return datetime.now(timezone.utc).replace(tzinfo=None)
  ```
- **触发路径**：绝大多数状态转移通过 `execute(update)` 显式传 `updated_at=_now()`（应用 naive UTC），但个别 ORM 属性赋值路径会落到 DB 的 `CURRENT_TIMESTAMP`。若 PostgreSQL 容器 `timezone` 非 UTC（compose 未显式设置，默认继承宿主/镜像），`recover_stale_tasks` 的 `updated_at < cutoff`（cutoff 基于应用 UTC）会产生时区偏移，超时判定提前/延后 1~8 小时。
- **建议**：compose 显式设置 `db.environment: TZ=UTC`（或 `PGTZ=UTC`）；或将 `onupdate` 统一改为应用侧 `_now()`，杜绝 DB 时间源混入。

## D. 审查后新增发现（用户报告，2026-09）

### D-1｜P1｜Emby 影视库跳转播放 URL 缺 `serverId` 参数 → 空白页（用户实测）

- **定位**：`backend/app/services/emby.py:229`
- **证据**：
  ```python
  # emby.py:229  emby_web_url 只拼 id，未拼 serverId
  "emby_web_url": f"{base}/web/index.html#!/item?id={item_id}",
  ```
- **用户实测对照**（NasTools 可正常跳转播放页）：
  ```
  NasTools:  http://192.168.3.31:8096/web/index.html#!/item?id=28758&serverId=d52a1f41ca834ad8a2ba410f1c0cd8db
  本系统:    http://192.168.3.31:8096/web/index.html#!/item?id=28758          ← 缺 &serverId=，打开是空白页
  ```
- **根因**：Emby web 前端的 item 详情路由 `#!/item?id=X&serverId=Y` 依赖 `serverId` 定位后端服务器实例；缺该参数时前端无法初始化 → 空白页。后端当前**完全没有**获取 Emby serverId 的代码（grep `System/Info` / `ServerId` 零结果）。
- **触发路径**：Emby 影视库展示页（`frontend/src/views/EmbyLibraryView.vue`）点击任意条目的「跳转播放」→ 打开 `emby_web_url` → 空白页。必现。
- **建议**：
  1. 新增获取 serverId 的能力：调用 `GET {base}/System/Info/Public`（Public 端点，**无需 api_key**），取其 `Id` 字段即为 serverId；模块级惰性缓存（serverId 恒定不变，一次获取全局复用）；
  2. `emby_web_url` 改为 `f"{base}/web/index.html#!/item?id={item_id}&serverId={server_id}"`；
  3. 获取失败时降级策略：不抛异常阻断列表，返回 `emby_web_url=None`（前端隐藏跳转入口）或记录 warn 后省略 serverId（保持现状）；建议前者，避免给用户一个必现的空白页链接。
